## 409 AUTH_SESSION_LIMIT 死锁：穷尽 API 旁路后确认无解

上游 https://api.aihuobao.cn（v1.0.0-rc.24）管理员 chatfire 仍锁定。
本轮把所有 API 自救路径实测了一遍，**全部不通**，结论钉死：

| 尝试 | 结果 |
|---|---|
| `/api/user/refresh`、`/api/auth/refresh`、`/api/user/login/refresh` | 404 不存在 |
| login 带 `remember:false` / `session:false` / `stateless:true` | 仍 409 |
| HTTP Basic 直取 `/api/user/token` | 401 |
| `/api/user/sessions`、`revoke-others` | 401（要 access_token） |
| `/api/user/logout`、`sessions/revoke-all` | 404 |
| 邮箱找回 `/api/verification` | 200 但 `invalid SMTP account`，上游未配 SMTP |
| `/api/option/` 改会话上限配置 | 401，改配置也要先登进去 |

站点登录能力实测：`email_verification/github_oauth/wechat_login/telegram_oauth/
linuxdo_oauth/passkey_login` **全 False**，只开密码登录 + `register_enabled=True`。
新注册的是普通用户，无权清他人会话，提权又需管理员权限 —— 同样循环。

**死锁本质**：清会话接口要 access_token → 拿 token 必须 login → login 被会话数
硬拒绝。闭环，API 层无解。

**唯一出路是改库**（或用另一个 root 账号抬 auth_version，但本实例没有备用管理员）。

### 本轮改进

`scripts/fix_session_limit.py --sql <用户名>`：
- 账号名直接填入，用子查询定位 uid，**不再有 `<uid>` 占位符需手工替换**
  （死锁时人在慌乱中操作，少一步手改就少一次改错行的机会）
- 补齐 MySQL / PostgreSQL / SQLite 三方言 —— 原先只有 MySQL 语法，
  `UNIX_TIMESTAMP()` 在 SQLite 上直接报错，而 SQLite 是 new-api 默认部署常用
- 备份命令、Redis 缓存陷阱、429 签发窗口限流区分都写进输出

`DEPLOY.md` 排查章节重写。原文写「配置 PAT 后重启即可」是**误导**：
PAT 要在前端生成，而进前端就得先 login，正是被挡住的那步。已明确区分
「还能登进去」（工具自动清理并打印 PAT）与「已死锁」（只能改库）两种情况。

## PAT 会被静默作废的两个触发点（今天连中两次）

`GET /api/user/token` **每次调用都重新生成 PAT 并作废旧值**。加上 auth_version，
一共两个触发点：

1. 抬升 `auth_version`（clear_sessions.py 清理管理员本人时）→ PAT 立即 401
2. **再次调用 `GET /api/user/token`** → 旧 PAT 当场失效，即使是自己调的

第 2 点今天中了一次：换完 PAT 写进 .env 后，又有调用走到 `_admin_login()` 触发轮换，
导致 .env 里的值变成过期值。表现是 BFF 返回「服务暂时不可用」而不是「兑换码不存在」
—— **查卡失败被 _assert_redeemable 转成 503，症状看起来像上游挂了，实际是凭证过期**。

排查要点：症状是「所有兑换码都返回 服务暂时不可用」时，先验 PAT：
```bash
curl -s "$NEWAPI_BASE_URL/api/user/self" -H "Authorization: Bearer $NEWAPI_ADMIN_PAT" \
     -H "New-Api-User: 1"
```
401 就是 PAT 过期，走「login → GET /api/user/token → 写 .env → DELETE 会话」四步换新。

**配了 NEWAPI_ADMIN_PAT 后 BFF 不会主动轮换**（`_load_admin_cred` 优先读 env 直接返回，
不走 `_admin_login`）。所以只要不手工再调 `/api/user/token`，env 里的 PAT 就稳定。

## GHCR 镜像未生成的原因 + .gitignore 恢复

用户问「GitHub 自动生成的镜像/package 在哪」。**原因是仓库零 tag**：
`release.yml` 触发条件是 `on: push: tags: ["v*"]`，本地与远端 `git ls-remote --tags`
均为空，工作流从未运行，所以 Packages 一栏空。工作流文件本身已在 origin/master 上。

发布方式：`git tag -a v0.1.0 -m "..." && git push origin v0.1.0`
产出三个 tag：`0.1.0` / `0.1` / `sha-<short>`（semver pattern 会剥掉 `v` 前缀）。

两个前置条件（易漏）：
1. Settings → Actions → Workflow permissions 不能是 read-only，否则 `packages: write`
   声明被仓库级设置覆盖，登录 GHCR 那步 403
2. GHCR 新包默认 private，需到 Package settings 改 Public 才能免登录 pull

冒烟步骤会校验 `/healthz` 的 version 字段包含 tag 名，打 tag 前建议本地
`docker build --build-arg APP_VERSION=v0.1.0` 验一遍，避免 CI 到最后一步才红。

### 无 gh CLI 时查 Actions / GHCR 的办法（本机没装 gh）

```bash
curl -s "https://api.github.com/repos/<owner>/<repo>/actions/runs?per_page=5"
# GHCR 匿名查 tag（公开包才行）
TOKEN=$(curl -s "https://ghcr.io/token?scope=repository:<owner>/<repo>:pull&service=ghcr.io" | jq -r .token)
curl -s -H "Authorization: Bearer $TOKEN" "https://ghcr.io/v2/<owner>/<repo>/tags/list"
```

### 放开「只在 tag 时发布」的改动（本轮）

用户要求主干 push 也发镜像。改 `release.yml`，**四处连带修改，缺一处就出问题**：

1. `on.push` 加 `branches: [master, main]` + `workflow_dispatch`
2. **`latest` 必须锁死在 tag 事件**：`type=raw,value=latest,enable=${{ github.ref_type == 'tag' }}`
   —— metadata-action 默认规则会让主干推送也移动 latest，生产 `pull latest`
   就会拿到未经发布决策的代码，且无法回滚到「上一个正式版本」。这是本次最关键的一处。
3. 新增 `计算版本号` step（id=ver）：tag 事件用 ref_name，branch 事件用
   `<branch>-<sha前7位>`。**不能直接用 `github.ref_name`** —— 主干推送时它是
   「master」，注入镜像后 `/healthz` 只显示 master，无法回溯具体提交。
   原有 3 处 `github.ref_name`（两个 build-arg + 冒烟校验）全部换成 `steps.ver.outputs.value`。
4. `concurrency` 用 `cancel-in-progress: ${{ github.ref_type == 'branch' }}`：
   主干连推可取消，tag 发布不可取消（中途掐掉会留下推了一半的清单）。

已用 pyyaml 校验两个 workflow 语法有效；emoji 门禁通过（30 文件 0 违规）——
门禁的 `targets()` 扫描模式不含 `.github/**`，改 workflow 注释不受其约束。

**遗留的重复构建问题**：ci.yml 与 release.yml 现在都监听主干 push，
同一次 push 会跑两遍完整门禁 + 两遍镜像构建（约 2 倍 Actions 分钟数）。
已向用户说明，等其决定是否把 ci.yml 收窄为只管 pull_request。
