## 修复 Cookie 明文 PAT 泄露（同日第二项，高危）

**漏洞**：`itsdangerous.URLSafeTimedSerializer` 只**签名**不**加密**，载荷是
base64 明文 JSON。实测：`token.split(".")[0]` 做 urlsafe_b64decode，
**不需要 SECRET_KEY 就能直接读出用户 PAT**。

原注释「被中间人抓到等于账号失守」低估了范围 —— 实际泄露面包括 devtools、
崩溃转储、把请求头贴进工单、CDN/WAF 请求留存、用户截图求助。

**修法**（用户拍板：服务端加密 + 不做旧格式兼容）：
- `app/security.py` 重写为 AES-256-GCM。格式 `v2.<nonce>.<密文>`，
  密钥由 SECRET_KEY 经 HKDF-SHA256 派生（info 做域分离），nonce 每次随机 12 字节，
  scheme 作为 AAD 一并认证。GCM 的 tag 同时替代原签名的防篡改能力。
- 签发时间 `iat` 加密进载荷，服务端判过期。**不能只靠 Cookie max_age** ——
  那由浏览器执行，攻击者拿到 Cookie 值后可无限期重放。
- 载荷结构校验（缺 uid/username/pat 判 401），避免业务层炸 KeyError 变 500。
- `requirements.txt`：移除 `itsdangerous`，加 `cryptography==43.0.3`（钉死小版本）。
  CI 装的是 requirements-dev.txt，它 `-r requirements.txt`，无需另改。
- `tests/test_session_crypto.py` 新增 17 个用例，核心断言是「PAT 不得以任何
  base64 编码形式出现在 Cookie 里」。
- 文档全量同步：SECRET_KEY 的定位从「签名密钥」改为「加密密钥」，
  并写明**轮换该值会让全部在线会话失效**。

### 关键决策记录

- **不做旧格式兼容**：兼容期内旧的明文 Cookie 仍有效 = 漏洞没关。
  用户认可强制登出一轮是正确的安全处置。
- **`_aes_key()` 不缓存**：SECRET_KEY 在测试里会被 monkeypatch，缓存会让改写失效。
  HKDF 单次 HMAC 开销可忽略。
- **`/readyz` 的 `_secret_key_strong()` 直接复用**：加密对密钥强度的要求比签名
  更实质，原有的空值/短值/弱值黑名单正好适用，只更新了注释表述。

### 踩坑

- `pip install cryptography` 首次退出码 137（SIGKILL）。改 `run_in_background`
  跑通，实际下载 6.2MB wheel 耗时约 2 分钟，是慢不是崩。
- 验证脚本里 `2>/dev/null` 把真实报错吞掉，只见空输出。定位手段：去掉重定向改
  `2>&1 | tail`。教训：调试期别用 `2>/dev/null`。
- mock store 的用户 uid 不是从 1 开始，`get_user_by_uid(1)` 返回 None。
  应按 `store.users["<name>"]` 取。

## 收尾：SameSite 可配置 + PYTHON_IMAGE 回退（同日第四项）

### SameSite 定为 lax（用户拍板）

之前一直挂着「是否收紧到 strict」。这轮读代码定了结论：

- `main.py:812-828` 三个支付回跳端点（`/usage-logs`、`/pay/return`、
  `/console/log`）**都不带 `Depends(require_session)`**，不读会话，
  既有用例 `test_pay_return_needs_no_login` 也印证。
- 但真正的风险不在这些端点，而在用户从支付网关点「返回商户」的**跨站顶层导航**：
  strict 下浏览器不带 Cookie → 落地显示未登录、看不到充值结果，
  **而钱已经到账**（走 notify_url）→ 极易被当成「付了钱没到账」引发客诉。
- lax 只放行顶层导航的 GET/HEAD，本项目所有写操作都是 POST，
  lax→strict 的安全增量很小，代价却是支付回跳必须重新登录。

改为 `BFF_COOKIE_SAMESITE` 可配（默认 lax），给「不做在线支付」的部署留口子。
新增 `config._choice()` 辅助函数，非法值静默回落到默认值 —— 因为浏览器会
忽略无法识别的 SameSite 值，等于降级到无防护，回落更可预期。
`security.py` 的 set_session / clear_session 都改为读配置。

## 修 CI e2e 的 `KeyError: 'data'`（同日第五项）

**同一个坑第二次踩到**，见本文件「踩坑记录」一节：上次是 pytest 夹具，
这次是 CI 里的 `scripts/e2e_redeem_mock.py`。当时只修了 `tests/conftest.py`，
漏了这个不走 pytest、自己起 uvicorn 的脚本。

现象：前 5 项 PASS，第 6 行 `s = (await c.get("/api/user/self")).json()["data"]`
抛 KeyError。根因不是脚本逻辑，而是两个工作流启动 uvicorn 时**没设
`BFF_COOKIE_SECURE=0`**，默认 True → 会话 Cookie 带 Secure →
httpx 按 RFC 6265 不在明文 http 上回传 → 每个后续请求 401 → 响应体无 data。

本地复现确认：8399 端口（默认 Secure）→ 同样 KeyError；
8398 端口（SECURE=0）→ 30/30 全通过。

**改动（3 个文件）**：
- `.github/workflows/ci.yml`、`release.yml` — e2e 步骤补 `BFF_COOKIE_SECURE: "0"`，
  **仅限该 step 的 env**，不影响 ci.yml:195 的生产写死项断言
  （那条读 docker-compose.yml，仍是 "1"，已复核）
- `scripts/e2e_redeem_mock.py` — 加 `preflight()` 启动自检
  （查 mock_mode → 试登录 → 查 cookie jar → 查会话可用）
  和 `self_of()` 统一取数，401 时打印可操作修复指引；
  6 处 `.json()["data"]` 换成 `self_of()`。
  第 120 行那处**故意保留裸调用**——它断言的就是 401 本身。

**教训**：这类「安全默认值收紧」的影响面要按*客户端*盘，不是按测试框架盘。
凡是以明文 http 访问自身服务的入口都得过一遍：pytest 夹具、独立脚本、
CI 工作流、本地调试命令、文档里的示例启动命令。
本次已在脚本 docstring 和启动示例里同步写明 SECURE=0。

**验证**：74 unit passed / e2e 30-30 passed / 2 个 YAML 解析通过 /
生产写死项断言复核未受影响 / 后台测试服务已清理（8398、8399 无残留监听）。

## 调用日志「积分」列全为「-」

**现象**：明细每行积分都是 `-`，但顶部「累计消耗积分 1,049」正常。
即「总额有值、每条都空」——这个反差就是定位关键。

**根因（两层）**：
1. 换算口径用错。`1 积分 = 50 quota`，单次小请求 quota 常在 10~49，
   过 `quota_to_points()`（向下取整）后恒为 0。而累计值是对**总 quota**
   一次性换算，不受取整影响，所以只有明细坏、总额好。
   修复：`config.quota_to_points_exact()`（保留 4 位小数），
   `app/main.py:417` 单条日志走 `PX`，`:432/:446` 聚合仍走 `P`。
2. 前端真值判断。`l.points ? ... : "-"` 对 0 走 `-`；且 `fmtPoints`
   会把 0.26 四舍五入成 `0`。改为 `Number(l.points) > 0` + `fmtPointsFine`。

**坑**：`static/app.js` 已修好，但 `dist/app.js:567` 还是旧代码。
线上挂的是 `static/`（`app/main.py:53`），`dist/` 是未同步的旧构建产物——
本次现象与它无关，但留着会误导排查，已同步一致。

**沉淀**：新增 `tests/test_log_points.py`（5 例），锁死
「消费明细 points 不得全为 0」与「累计为正时明细之和必为正」两条契约，
防止后续把 `PX` 改回 `P`。79 passed。

**通用教训**：聚合值正常不能证明单条正常。凡「先除后取整」的换算，
明细口径与聚合口径必须分开，且明细一律保留小数。

## 模型排行「标题说积分、看起来按次数排」

线上只挂 `static/`（`app/main.py:833`）。
**结论：dist/ 不是同步目标，别再往里对齐。**

**验证**：node --check 通过；用截图数据复现，旧口径四列全 0、
新口径 0.43/0.37/0.26/0.2；本例中积分序与次数序恰好一致，
这正是误判来源。79 passed。

**通用教训**：用户报「排序错了」时先验渲染，不要直奔比较函数。
数值被格式化成同一个值时，有序性在视觉上会转移到旁边那一列。

## 修 ruff S105 误报：豁免范围收窄 + 两个 ruff 使用陷阱

起因：`ruff check app tests` 报 `app/config.py:78 S105`（`SECRET_KEY_DEFAULT`
被判硬编码密码）。该值实为 `/readyz` 弱密钥黑名单的哨兵值，S105 属误报。

根因：`pyproject.toml` 原有 `"app/main.py" = ["S105"]` 豁免，注释还写着
「main.py:632 的 dev-only-secret-change-me」。该字面量后来被提取为
`config.SECRET_KEY_DEFAULT` 单一事实源，豁免规则没跟着搬 → main.py 侧空转，
config.py 侧裸奔。**教训：提取常量时要同步迁移 lint 豁免，否则豁免会漂移。**

改法（选行内 noqa 而非 per-file-ignore）：
- `app/config.py:83` — `SECRET_KEY_DEFAULT = "..."  # noqa: S105`
- `app/main.py:777` — `_FIX_SECRET`（修复提示文案，变量名含 SECRET 触发误报）
- `pyproject.toml` — 移除已空转的 `"app/main.py" = ["S105"]`，留注释说明去向
理由：config.py 是最容易被误塞真凭证的文件，整文件关 S105 等于永久放弃看护。
探针验证：新建 `PASSWORD = "hunter2-real-leak"` 仍被 S105 拦住。

### 陷阱 1：解释性注释里不能让 `noqa:` 出现在行首
我把理由写成 `# noqa: S105 —— 这不是密码...` 独立成行，ruff 把它当**真的
noqa 指令**解析，RUF100 报冗余。注释须改写为「行尾抑制 S105 的理由：...」，
避开 `noqa:` 前缀形态。

### 陷阱 2：`--select RUF100` 单跑会把有效 noqa 误判为冗余
`--select` 会**关掉其他所有规则**，于是针对 S105 的 noqa 被判
`Unused noqa (non-enabled: S105)`。必须用 `--extend-select RUF100` 保留项目
select。误报 4 个 → 正确姿势下只剩 2 个真冗余。
（顺手清掉 `app/observability.py:71,105` 两处 `# noqa: BLE001` —— 上一轮加
Logfire 时留的，项目 select 未启用 BLE001，改为普通注释说明宽泛捕获的意图。）

验收：`ruff check app tests` All checks passed；`--extend-select RUF100`
All checks passed；79 passed；关闭态 `setup()` 仍返回 False。

## Logfire 控制台无数据：`.env` 从未被加载（同日第六项）

**现象**：`.env` 里 `LOGFIRE_TOKEN` / `LOGFIRE_ENVIRONMENT=local` 都配好了，
Logfire 控制台却没有任何记录。

**根因**：全项目没有任何 `load_dotenv` 调用。`app/config.py` 只用
`os.getenv`，`.env` 从头到尾没人读。实证：`grep -rn "load_dotenv|dotenv" app/`
零命中；`python -c "from app import config; print(config.LOGFIRE_ENABLED)"`
→ `False`，而 `set -a; source .env` 后同一命令 → `True`。

之前接入 Logfire 时的验证全部走 `TestExporter` 或手动 `export`，
**绕过了配置加载这一层**，所以「埋点挂上了」和「token 读到了」被混为一谈。

**修法**：
- `app/config.py` 在模块级读取前 `load_dotenv(..., override=False)`。
  `override=False` 是关键：容器/CI 注入的真实环境变量必须优先于 `.env`，
  否则 compose 的 `${VAR:?}` 硬抦会被本地文件悄悄盖掉。
- `ImportError` 降级为「只读环境变量」而不是崩溃。
- `requirements.txt` 显式声明 `python-dotenv==1.0.1`。原先它只是
  uvicorn[standard] 的间接依赖，现在成了直接依赖，不声明等于赌传递依赖不变。

### 踩坑：加载 .env 后 3 个既有用例开始失败

`test_readyz_requires_admin_cred_in_real_mode` 断言 503 实得 200；
`test_log_points.py` 两例积分换算断言错位。

根因是 `.env` 里的真实值渗进了测试：`NEWAPI_ADMIN_PAT` 让「凭证缺失」
场景不再成立（用例用 `monkeypatch.delenv` 删环境变量，但 `importlib.reload`
会重新触发 `load_dotenv` 把值加回来）；`BFF_POINTS_PER_CNY` 改变了换算基数。

修法不是逐个屏蔽变量，而是加 `BFF_SKIP_DOTENV=1` 开关，
`tests/conftest.py` 在 import `app.*` 之前设置，让测试彻底不读 `.env`。
`LOGFIRE_TOKEN=""` 保留作第二道防线（防 token 从真实环境变量传入）。

**教训**：给配置层新增数据来源（`.env`、远端配置中心、密钥管理服务）时，
必须同步给测试留一个「关掉这个来源」的开关。否则测试结论会随开发者本机
文件内容漂移——本地过 CI 挂、或更糟的本地挂 CI 过，且测试流量会被上报到
真实可观测性项目污染线上数据。

### 验证
- 三条路径分别实测：生产路径 `LOGFIRE_ENABLED=True environment=local`；
  测试路径 `False`；`LOGFIRE_ENVIRONMENT=staging` 前缀运行得 `staging`
  （证明 `override=False` 真的让真实环境变量优先）。
- 起服务实测日志 `logfire 已启用 environment=local fastapi_traces=on`。
- 同进程 TestClient 打 `/healthz`+`/readyz` 并手动 span + `force_flush`，
  span 正常生成并投递。
- 79 passed，`ruff check` All checks passed。

**遗留（非代码问题）**：当前沙箱环境到 `logfire-us.pydantic.dev:443`
不通（直连与走代理均 10~12s 超时），故未能在控制台侧眼见数据。
用户本机网络正常时重启服务即应看到。

## Logfire 仍无数据：第二个断点在 compose（同日第七项）

上一项修完 `.env` 加载后用户反馈依旧没数据。**上一项的诊断不完整**——
只验证了宿主机 venv 路径，没查用户实际的运行形态。

**关键发现**：`lsof -i :8000 -i :8080` 显示监听者是 Docker，不是宿主机
venv。用户跑的是容器，所以「宿主机 venv 里 `LOGFIRE_ENABLED=True`」
这个结论对他的实际进程毫无意义。

**根因**：`docker-compose.yml` **没有 `env_file:`**，采用逐项显式声明的
`environment:` 白名单模式，而其中不含任何 `LOGFIRE_*` 条目 →
宿主机 `.env` 配得再对也进不了容器。

注意：本文件上方「修复 /readyz 503」一节写着「docker-compose 已有
`env_file: .env` 无需改」，**该记录是错的**，同日第三项改为纯生产编排时
已改成逐项声明。错误的记忆笔记直接导致这次多绕一轮。

**修法**：`docker-compose.yml` 的 `environment:` 段（原止于
`FORWARDED_ALLOW_IPS`）补两行透传：
`LOGFIRE_TOKEN: ${LOGFIRE_TOKEN:-}` / `LOGFIRE_ENVIRONMENT: ${LOGFIRE_ENVIRONMENT:-}`。
用 `:-` 而非 `:?`，可观测性缺失不该阻断启动。

**排掉的一个疑点**：容器是 `read_only: true`，怀疑 logfire 写
`.logfire/` 凭证目录会失败。实测在 `chmod a-w` 目录下 configure 正常返回、
且不创建 `.logfire`——显式传 `token` 参数时 logfire 不落盘。无需改 read_only。

### 新增 scripts/diag_logfire.py

按依赖顺序分四层定位，避免再靠猜：
L1 配置解析（含**扫 .env 原始文本区分「没配」与「被 # 注释」**，
后者从解析结果看与前者完全相同，是最易误判的一种）/ L2 依赖 /
L3 网络（从 token 的 `pylf_v1_us_` 前缀解析区域再选 host——
区域选错的表现与网络不通完全一样；用裸 socket+TLS 绕开代理变量测真实直连）/
L4 端到端（`--send` 才执行，含 `force_flush`）。

### 验证
- 脚本实测精确定位到 L3：L1/L2 全 OK，DNS 解析出 Cloudflare 三个 IP，
  TLS 握手超时。
- 容器式纯环境变量注入路径实测 `LOGFIRE_ENABLED=True environment=production`；
  刻意不传变量则得 `False`，**精确复现用户现象**。
- `docker compose config` 渲染确认两个变量已带上。
- 79 passed / ruff All checks passed / emoji 门禁 35 文件 0 违规。

**教训**：排查「配置没生效」类问题，第一步必须确认**目标进程的实际运行
形态**（容器 or 宿主机 or systemd），再决定验证哪条注入链路。在错误的
形态里验证会得出自信但无用的结论。次级教训：compose 用显式白名单模式时，
每次新增配置项都得同步加一行，这是该模式的固有维护成本——已在 environment
段落写注释提醒。
