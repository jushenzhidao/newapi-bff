## 评估「方案二：前端+BFF(Python)」并与 AI-PLATFORM-SOLUTION 对比
- 核实了 new-api（QuantumNous/new-api main 分支）真实鉴权机制，方案二的核心假设已过时：
  - 登录返回 `data.access_token`（JWT，**15 分钟 TTL**）+ `data.session`，无 `data.token` 字段
  - refresh token 走 HttpOnly Cookie `new_api_refresh`，刷新端点 `POST /api/user/auth/refresh`（有 SessionCookieOriginGuard）
  - 会话上限：UserSessionActiveLimit / IssuanceLimit，LoginSessionTTL 30 天，refresh 轮换 + 重放检测（30s 窗口）
  - PAT（`GET /api/user/token` 生成，存 users.access_token 列）可长期用于 Bearer 鉴权，无 New-Api-User header 要求
  - 易支付回调 `/api/user/epay/notify` 由 new-api 自己验签，notify URL 来自 ServerAddress/CustomCallbackAddress 配置，BFF 转发回调属多余且方案中未验签
  - `POST /api/user/`（AdminAuth 建号）响应不返回 user id；add_quota (`/api/user/manage`) 无幂等键
- 结论：方案二按原文实现会在登录 15 分钟后全站 401（未处理 access_token 刷新）；AI-PLATFORM 方案（BFF 影子账号 + PAT + 管理面加额）绕开会话语义，与源码事实吻合度高。
- 简单性对比结论：起步简单是方案二（改造后用 PAT 而非 session token），长期简单是 AI-PLATFORM（单应用可裁剪版）。
- 用户项目 newapi-bff 目前为空仓（仅 .git），尚未定稿选型。

## 兑换码登录（已完成）
- 需求：用户拿一张 new-api 兑换码即可直接使用，免注册、免邮箱
- **关键契约发现**：`GET /api/redemption/search` 的 keyword **不匹配 key 字段**（只匹配 name/id），
  实测传完整 key 返回 total=0 → 无法按码反查绑定账号，「查表找回」方案被排除，只能确定性派生
- 方案（`app/redeem_code.py`）：`username = "rc_" + HMAC(SECRET_KEY, normalize(code))[:16]`，
  `password = HMAC(SECRET_KEY, normalize(code)+"|pwd")[:20]`。normalize 去横杠转小写，
  `4EE5-EE69-...` 与 `4ee5ee69...` 归一到同一账号。用 HMAC 而非明文散列，无 SECRET_KEY 无法从用户名反推码
- 流程：派生账号存在→直接登录；不存在→建号→核销→到账；**核销失败立即 DELETE 删号回滚**，不留垃圾账号
- 绑定升级：`PUT /api/user/` 改用户名+密码，uid 不变，余额/Key/日志全保留；禁止占用 `rc_` 前缀防抢注
- **密码长度上限坑**：new-api 对密码有 max 校验，实测 20 位通过、24 位报
  `Invalid input Key: 'User.Password' ... failed on the 'max' tag`。派生密码从 32 位改为 20 位（仍有 80bit 熵）；
  注册/绑定接口前后端同步加 8-20 位校验
- 新增契约：`DELETE /api/user/:id`（管理员删号，立即生效）、`PUT /api/user/`（改账密，重名报 Duplicate entry）
- E2E：真实环境 28 项断言全通过；mock 21 项全通过（脚本用 secrets 随机后缀，可对同一服务反复跑）

## ⚠️ new-api 会话上限（最高危坑，已踩中并根治）
- 现象：反复登录管理员后，`POST /api/user/login` 永久返回 `409 {"code":"AUTH_SESSION_LIMIT"}`，
  BFF 的建号/加额度/兑换码全线瘫痪
- 根因（读 service/auth_session.go 源码核实）：每次 login 新建一条 UserSession，
  `activeCount >= UserSessionActiveLimit(50)` → **硬拒绝，不淘汰最旧会话**，`LoginSessionTTL` 30 天，**无管理员豁免**
- 死锁点：会话管理接口（GET/DELETE `/api/user/sessions`、`POST /api/user/sessions/revoke-others`）
  要求真实 dashboard 会话上下文，**PAT 调用返回 403** → 登不进去就没法用 API 自救
- **三重防护（已实装）**：
  1. 借了就还——`login()` 换到 PAT 后立刻 `DELETE /api/user/sessions/{sid}`（必须用 access_token，PAT 不行）。
     实测删会话后 PAT 依然有效（PAT 走 users.access_token 列，不经过会话系统）。**验证：连续 10 次登录净增 0 会话**
  2. `NEWAPI_ADMIN_PAT` + `NEWAPI_ADMIN_UID` 环境变量直供 PAT，BFF 完全不调 login，从根上不消耗配额（生产必配）
  3. PAT 落盘 `data/admin_cred.json`（0600），进程重启不消耗会话配额
- 恢复工具 `scripts/fix_session_limit.py`：自动检测实例开启了哪些登录方式并给出方案；
  `--sql` 输出 DB 修复语句（表 `user_sessions`，条件 `status='active' AND expires_at > now`，
  改 `status='revoked'`；启用 Redis 时需重启 new-api 才生效）
- 报错分层：用户只看到「服务暂时不可用」，完整运维指引只进 logger.error
- **当前状态：管理员 chatfire 仍处于锁定态**，实例只开了密码登录（无邮箱找回/OAuth/Passkey），
  需用另一管理员账号抬 auth_version 或直接改库恢复
